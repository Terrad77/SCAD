# v0.13.1 — browser pipeline runs

Scope: explicit Run from Overview, durable execution status and bounded event history. Approve/Reject, browser Resume, force regeneration, provider configuration UI and lock recovery are excluded. Existing CLI human review remains available. This is the first v0.13 increment, not the complete browser review workflow.

ProjectRuns owns asynchronous execution independently of the HTTP request. POST /api/projects/:id/runs accepts only UUID requestId and expectedVersion. Admission occurs under the shared project write coordinator after validating metadata, snapshot, artifact entries and pending revisions. GET returns the latest journal plus whether this server can currently attest active ownership. Authentication, exact Origin/Host and body limits are inherited from the workspace API. Browsers cannot supply paths, shell commands, providers, force flags or approval decisions.

Runs use the existing documentary orchestrator, environment provider configuration and artifact export. An awaited stage-start observation hook records generation boundaries. The approval gate records WAITING_REVIEW and throws a private suspension signal after the pipeline has saved its candidate, before any approval or downstream execution. Ownership is then released so an operator can continue through the interactive CLI. The journal remains historical WAITING_REVIEW even if CLI work later progresses; browser reconciliation and Resume are future scope. Completion describes execution, never the audit verdict.

Journals live outside project directories in .scad-runs/<case-normalized-project-hash>/<requestId>.json with a latest.json UUID pointer. Atomic same-filesystem replacement preserves bounded structured events. Request receipts remain available after newer runs and safe replay does not execute again. RUNNING or WAITING_REVIEW prevents another new browser run. Different server instances cannot attest another instance's execution and display Execution unverified; PID/timeouts never reclaim ownership. Incomplete/corrupt journals or stale coordinator locks require operator inspection, not automatic replay. A crash between journal and pointer persistence may leave an orphan receipt; recovery must inspect both. Journals are retained across Trash/restore.

Supported deployment is the existing single-machine local filesystem with cooperating upgraded entrypoints. Run the viewer from the repository root so relative prompt files resolve. No guarantee covers power-loss durability, manual external file edits, old binaries or direct engine calls. Graceful ViewerServer.close waits for owned jobs; process termination may leave interrupted ownership. There is no cancellation endpoint in this increment.

UI: existing system typography, semantic colors and 44px controls; one bordered operational panel in Overview. Status is announced concisely, log is a native disclosure with local scrolling and wrapped long signatures. Polling is sequential every 1.5 seconds only while this server attests active execution, and is disposed on navigation. Request errors retain the UUID for safe retry. Check status recovers a failed read; Refresh materials reloads the saved snapshot without automatically running anything. Page reload retains server journal state, not an unacknowledged browser request identity. No dependency or animation is added.
