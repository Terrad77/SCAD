# SCAD — проектирование локального рабочего интерфейса

Дата: 3 октября 2026 года.

Базовая версия: v0.10, `main @ 54602bcc0cd9b5dc7b710da080427743ff908c60`.
На этой базе выполнены 523 теста в 45 файлах и проверки build/types/lint/format.
Этот документ описывает предлагаемые следующие этапы; они ещё не реализованы.

## 1. Решение и цель

Продолжить развитие SCAD как локального приложения для одного пользователя.
Существующие JSON-файлы остаются источником состояния. Облачная инфраструктура,
новая база данных, синхронизация устройств и совместная работа исключены из scope.

Следующий полезный результат — рабочий интерфейс, в котором автор фильма может:

1. Понять состояние проекта и доступность его материалов.
2. Прочитать сценарий и увидеть, чем поддерживается конкретная реплика.
3. Найти замечание SelfCheck и перейти к затронутым репликам и кадрам.
4. Позже — согласовать конкретное исправление и проверить его результат.

Интерфейс вызывает существующее ядро. Он не вводит самостоятельную логику
reasoning, проверки фактов, присвоения knowledge labels или публикации revisions.

Рекомендуемый порядок: v0.11 — просмотр; v0.12 — управляемые действия;
после этого — проверяемый пакет передачи в производство.

## 2. Основные пользовательские сценарии

### Открыть проект

Автор выбирает существующий проект. Обзор показывает вопрос фильма, текущие
артефакты, последний reasoning cycle, состояние production и незавершённую revision.
Отдельно отображаются результат аудита и актуальность артефактов.

«Актуально» не означает «прошло проверку». Актуальный аудит может содержать FAIL
или UNKNOWN. Завершённая revision не означает устранение всех issues.

### Проверить реплику

Автор выбирает предложение сценария. Боковая область показывает его knowledge
label, claims, явные ссылки v0.9 и связанные кадры. От claims можно перейти к
evidence и источникам через существующую цепочку traceability.

Разорванная ссылка остаётся видимой. Отсутствие evidence не заменяется подходящим
текстом из другой части проекта. Декларация hypothesis/uncertainty/constraint
отображается отдельно от подтверждающей цепочки.

### Разобрать issue

Автор видит причину, severity, route, привязку к снимку и связанные идентификаторы.
Issue из прошлой версии помечается как исторический. Его решение и подтверждение
устранения сохраняются независимо от наличия новых замечаний.

В v0.11 доступен просмотр существующего журнала. Открытие экрана не выполняет
`issues sync`, новый аудит с записью, регенерацию или reasoning.

### Согласовать исправление — v0.12

Автор выбирает issue, действие и обоснование. Для fix сначала просматривает
конкретный plan, затем подтверждает предложение. Дальнейшие checkpoints проходят
через существующий revision engine: narrative, visual, SelfCheck и final review.

После публикации issue остаётся AWAITING_VERIFICATION. Отдельная команда проверки
может подтвердить устранение по правилам v0.10. Defer и dismiss показываются как
решения автора, без зелёной отметки «проблема исправлена».

Research/reasoning означают передачу согласованного запроса в существующий journal.
Интерфейс отдельно показывает передачу запроса и запуск reasoning. Он не обещает,
что запрос заставит policy выбрать определённое исследование.

## 3. Экраны

### Список проектов

Название, вопрос и возможность открыть проект. Статус загрузки отражает отсутствие
или повреждение файлов, а не скрывает проблемный проект из списка.

### Обзор проекта

Последовательность стадий, текущие результаты, актуальность, последний цикл,
незавершённые revisions и краткая сводка issues. Не вводить единый процент
«готовности фильма»: он смешал бы техническое завершение и качество доказательств.

### Сценарий и кадры

Основная область — читаемый сценарий. Выбор реплики открывает связи и замечания.
Кадры показывают описание, visual type, source и связь с репликами. Media preview,
генерация изображений, озвучка и монтаж пока исключены.

### Проверка и issues

Результаты семи production checks, отдельно structural/semantic reference report,
затем сохранённые issues с фильтрами по severity, disposition и свежести снимка.
Исторические scope observations не выдаются за новую проверку файловых записей.

### История изменений

Revision ID, status, plan и diff, без возможности выдавать старый снимок за текущий.
Во время PUBLISHING отображается незавершённая публикация; смешанный набор файлов
не представляется согласованным production snapshot.

Создание проектов, редактирование и кнопки запуска появляются на следующем этапе.
В первой версии интерфейса не показывать неработающие кнопки этих действий.

## 4. Архитектура

```text
Локальный браузер
        |
        v
Локальный HTTP-сервер
        |
        v
Application services: чтение / команды / checkpoints
        |
        v
Существующие engines и scoped memory
        |
        v
JSON memory и output проекта
```

Сервер работает на loopback. Браузер получает представление проекта через API,
а не прямой доступ к файловой системе. Сервер загружает проект из настроенного
корня SCAD_DATA_DIR; запросы не содержат произвольных путей.

Не запускать интерактивный CLI из веб-интерфейса и не разбирать его консольный вывод.
Application services вызывают engines и передают им MemoryStore и ApprovalGate.
CLI и HTTP становятся двумя способами обратиться к одним операциям.

Предлагаемые модули, названия которых уточняются при реализации:

- `src/application/project-reader.ts` — валидированное чтение и display DTO.
- `src/application/production-service.ts` — операции существующих production engines.
- `src/application/project-write-coordinator.ts` — общий контроль записи, v0.12.
- `src/server/` — HTTP transport и выдача локального интерфейса.
- `src/ui/` — сценарий, связи, аудит и история.

Для первого viewer достаточно Node HTTP и небольшого TypeScript-интерфейса.
Выбор UI-фреймворка не должен расширять scope: сначала проекция состояния и навигация.
Хранилище и алгоритмы ядра не меняются ради удобства компонентов.

## 5. Контракт чтения — v0.11

Read API возвращает display DTO и `readVersion`, рассчитанный по точному прочитанному
набору исходных файлов. Пример логических операций:

- список проектов;
- обзор выбранного проекта;
- сценарий и shot list;
- trace для конкретного subject ID;
- текущая диагностика и сохранённые issues;
- revisions и diff выбранной revision.

`readVersion` — версия прочитанного представления, а не новый epistemic signature.
Он не заменяет существующие signatures и dependency checks.

Reader различает MISSING, CORRUPT, UNVERIFIABLE и корректный артефакт. Критичные
чтения используют readRaw и валидацию, поскольку get в текущем MemoryStore может
возвращать null и при ошибке чтения/парсинга.

Для согласованного представления reader читает исходные файлы и повторно сверяет
их raw hashes перед ответом. При изменении набора выполняет ограниченный повтор,
затем явно сообщает нестабильный снимок. Это обнаружение гонки, а не обещание
транзакционного snapshot файловой системы.

Во время незавершённой публикации доступны её status и journal/diff. Overview
не заявляет целостность текущего набора canonical files. Любые производные проверки
в режиме просмотра выполняются только в памяти и не обновляют сохранённый аудит.

Парсинг display DTO не должен изменять исходные артефакты или их подписи.
Нельзя восстанавливать подписанный context из заново упорядоченного UI JSON.
HTML, Markdown и внешний текст отображаются без выполнения встроенного кода.

## 6. Контракт команд и согласования — v0.12

Каждая изменяющая команда содержит project ID, явный command kind, уникальный
request ID и ожидаемую readVersion. Рationale обязателен там, где его требует
issue workflow. Доступные команды задаются allowlist, а не arbitrary stage/key/path.

Перед эффектом сервер получает исключительное владение записью проекта и повторно
проверяет состояние. Устаревшее предложение отклоняется; пользователь получает
обновлённый снимок и снова рассматривает действие. Фонового перепланирования нет.

Checkpoint содержит review ID, operation/revision ID, доступные решения и точные
artifact/dependency signatures. Ответ браузера допустим только для текущего
checkpoint и показанных signatures. Решение из другой вкладки или прежнего draft
не засчитывается. Authority human присваивается сервером после явного действия
локального пользователя, а не принимается произвольным полем запроса.

WebApprovalGate реализует существующий ApprovalGate. ApprovalLedger и decisions
остаются источниками governance; транспорт не ведёт второй журнал согласований.
Разрешённые manual edits проходят существующую схему, guard и повторный review.
Context, SelfCheck, issue decision и final checkpoint остаются нередактируемыми
там, где это уже требует ядро.

Закрытие браузера не означает approve, reject или cancel. Checkpoint остаётся
ожидающим; возвращение в интерфейс показывает то же предложение. После перезапуска
сервера незавершённая операция требует явного resume и переоткрывает checkpoint
через существующий engine. Runtime promise не является механизмом восстановления.

Request ID устраняет повторную отправку одного действия. Повтор возвращает ссылку
на ту же operation. Новый ID не позволяет обойти pending revision или staleness.
При неопределённом результате сначала проверяется domain journal, затем применяется
его идемпотентный resume; внешние эффекты не повторяются вслепую.

## 7. Один писатель и длительные операции

Текущая архитектура допускает одного писателя на проект. Очередь в HTTP-процессе
сама по себе этого не обеспечивает: CLI — другой процесс.

До включения mutating API общий координатор записи обязателен для всех публичных
пишущих entrypoints CLI и сервера. Пока он не внедрён, HTTP остаётся read-only.

Владелец удерживает право записи на время генерации, review и публикации.
Чтение разрешено с обозначением DRAFT/PUBLISHING. Второй писатель получает понятное
«проект занят» и ID текущей операции. Другой проект может обрабатываться отдельно.

Блокировка должна быть межпроцессной, с документированной поддержкой Windows.
Нельзя снимать её только по таймеру или PID: процессы могут надолго ждать решения,
а PID переиспользуются. Проверка владельца и recovery незавершённого domain journal
проектируются и тестируются до включения команд. Сетевые файловые каталоги исключены.

Если понадобится durable run metadata, он хранит command/request ID, ссылку на
domain operation и транспортный status. Он не дублирует candidate artifacts,
approval verdicts или reasoning decisions как независимую истину.

Progress содержит текущую стадию и checkpoint, без выдуманного процента завершения.
Отмена до публикации и recovery во время PUBLISHING имеют разные правила: нельзя
предлагать «отменить всё» после частично выполненной публикации без поддержки ядра.

## 8. Локальная граница доступа

Сервер не слушает внешние интерфейсы. Host/Origin проверяются; wildcard CORS не
включается. Локальная сессия получает временный capability token для доступа к API,
а запросы команд требуют подтверждённого same-origin контекста.

Это защита локального transport, а не система аккаунтов или ролей. Не выдавать
через API provider keys, .env, произвольные файлы или содержимое вне каталога проекта.
Идентификаторы проектов проходят проверку принадлежности настроенному корню,
включая защиту от traversal и обхода через ссылки/junctions.

## 9. Разделение на этапы и критерии приёмки

### v0.11 — local project viewer

Scope: запуск локального сервера; список существующих проектов; overview;
сценарий/кадры; trace navigation; SelfCheck/issues; revisions/diff; понятные
состояния отсутствующих, повреждённых и меняющихся материалов.

Exclusions: все mutating endpoints, создание/удаление проекта, запуск reasoning,
sync issues, редактирование, approvals, job queue, новая БД и media generation.

Приёмка:

1. Открытие всех экранов сохраняет memory и output побайтно.
2. Fixture с разорванной evidence chain показывает точное место разрыва.
3. Актуальность, audit verdict и disposition issue отображаются раздельно.
4. DRAFT/PUBLISHING, corrupt JSON и смена файлов во время чтения не выглядят PASS.
5. Навигация sentence → claim → evidence → source и sentence → shots работает.
6. Историческая revision и issue явно отличаются от текущих материалов.
7. API отказывает внешнему origin и пути вне настроенного корня.
8. Существующие CLI и регрессионные тесты продолжают проходить.

### v0.12 — interactive production review

Scope: общий межпроцессный writer coordinator; issue sync/dispositions;
revision plan/apply/resume/reject; WebApprovalGate; просмотр и подтверждение
diff; explicit issue verify; экспорт только canonical completed snapshot.

Запуск самостоятельного reasoning из браузера лучше выделить в последующий
малый increment. В v0.12 можно согласовать handoff и показать дальнейшую CLI-команду,
сохранив явный запуск и действующие ограничения v0.10.

Приёмка:

1. CLI и сервер не могут одновременно писать один проект.
2. Double click/retry не создаёт второй эффект для того же request ID.
3. Approval для прежней подписи не авторизует изменившийся draft.
4. Reload/disconnect не принимает решение за человека.
5. Server crash восстанавливается через сохранённые domain journals.
6. Повреждение protected state не скрывается повторной генерацией.
7. Defer/dismiss не закрывают issue; UNKNOWN не подтверждает устранение.
8. Исторический completed snapshot не перезаписывает более новый output.

### Следующий функциональный этап — production delivery package

Проверенный экспорт выбранной completed revision: сценарий, shot list, source/evidence
references, audit, approvals и manifest содержимого. Потребуются правила включения
материалов и проверка соответствия снимку. Это отдельный этап, не генерация видео.

## 10. Риски и решения

- Несогласованный filesystem snapshot: повторная проверка raw hashes и явный отказ
  выдать изменяющийся набор за согласованный; writer coordination перед командами.
- Параллельный запуск CLI: общий lock для всех публичных писателей, не только UI.
- Повтор effect после timeout: request identity плюс domain journal reconciliation.
- Approval старого draft: server-side signatures и повторная проверка dependencies.
- Ложное ощущение качества: отдельные freshness, audit verdict и issue disposition.
- Перенос policy в интерфейс: UI только отображает и вызывает существующие engines.
- Превращение diagnostic в evidence: текущая граница v0.10 сохраняется.
- Непроверяемая семантика: UNKNOWN остаётся видимым; UI не вводит собственный PASS.
- Разрастание MVP: сначала read-only viewer, затем production actions.

## 11. Рекомендуемая ближайшая задача

Реализовать v0.11 local project viewer по разделу 9. Начать с project-reader и его
read-only contract, затем HTTP API, затем интерфейс сценария/trace/issues. Контракты
v0.12 учитывать при DTO design, но не реализовывать speculative mutating APIs.

Этот порядок даёт полезный рабочий инструмент на текущем ядре и позволяет отдельно
проверить механизмы записи и согласований перед открытием их в интерфейсе.


## 12. Реализованный v0.11

Локальный viewer реализован без Supabase и новых зависимостей. После сборки
запускать из корня репозитория:

```powershell
node dist/cli/bin.js viewer --port 4311
```

Открыть напечатанный адрес с 127.0.0.1. По умолчанию читается data/projects;
SCAD_DATA_DIR позволяет выбрать другой корень проектов. Ctrl+C останавливает сервер.

Доступны поиск проектов, обзор состояния, сценарий, кадры, связи и источники,
сохранённый и независимый аудит, фильтры issues, история revisions и diff.
Найденная ссылка не означает подтверждённую семантику. UNKNOWN сохраняется.

ProjectReader читает только фиксированный список артефактов. Он не создаёт файлы,
не запускает providers и не синхронизирует issues. Двойное чтение обнаруживает
изменение снимка; после трёх неудачных попыток возвращается 409. Это проверка
стабильности чтения, а не межпроцессная транзакция. Во время PUBLISHING текущие
production-материалы скрыты, чтобы не показывать частично опубликованный набор.

Сервер принимает только GET и слушает 127.0.0.1. API использует временный session
capability; проверяются Host и Origin. Пути ограничены корнем проекта, junctions
и symlinks запрещены, размер артефакта ограничен 16 MiB, снимка — 64 MiB.
Текст проекта выводится через textContent, внешние ссылки ограничены HTTP(S).

Редактирование, запуск генерации, согласования и действия над issues остаются
следующим этапом v0.12 после реализации общей координации записи.
