# v0.13.2 — Research review

Scope: review one saved ResearchBundle from a browser-created WAITING_REVIEW checkpoint, then explicitly Approve or Reject. No browser Resume, regeneration, edits, other-stage approvals, provider setup, cloud accounts or automatic continuation.

New runs persist a structured checkpoint identity: raw candidate content signature, the existing pipeline dependency signature (empty upstream for Research), and title/question signature. Older v0.13.1 checkpoints without this identity remain inspectable but require CLI review. Browser inspection returns the full saved candidate, sources/evidence and its snapshot version. Schema validation does not strip unknown candidate fields before signing or rendering full JSON. Unsafe URLs are not made clickable.

POST /api/projects/:id/review requires the existing session capability and exact local Origin, a UUID requestId, runId, expectedVersion, both proposal signatures, action and note. Reject requires a nonblank reason. Unknown fields are refused. Under shared ownership the command re-reads the current checkpoint, artifact, inputs, revision state and snapshot. Drift, an existing approval, an already decided checkpoint, unsafe memory entries, corrupt ledger or a pending revision prevents a new decision.

Approve records authority=human through ApprovalLedger and its governance-scoped store, using the exact signatures that Pipeline expects. An optional decisionId extension is persisted with that record for crash reconciliation; existing approval matching remains content/dependency based. Reject records its reason in the run decision/receipt, preserves the candidate and grants no approval. Both leave the run stopped. CLI rejection/regeneration remains a separate explicit operator action; the browser rejection is a disposition for history, not a request to delete materials.

Each checkpoint has an exclusive prepared .decision.json receipt and a .decision-done.json completion digest beside its run journal. Only replay of the same normalized request can finish a prepared decision. A committed ledger record with the exact decision ID/body reconciles a crash before the run journal; an already-written journal does not gain duplicate events. A completed receipt returns its historical result without overwriting later ledger/artifact changes. Conflicting or malformed receipts fail closed. Recovery with a lost request identity requires operator inspection; the UI does not silently replay a decision on load. Power-loss durability and manual external writers are outside the existing local-filesystem contract.

The UI separates recorded decisions from current candidate content and shows original checkpoint identity as well as displayed candidate identity. Later edits do not inherit the old approval. Busy controls, persistent errors, immutable submitted values for retry, rejection validation/focus and explicit draft-discard reload are included. Navigation disposes requests' UI updates; server decisions continue under ownership. Review text and forms have bounded reading width; native disclosure sections contain sources/evidence, full candidate JSON and signatures.

Windows correction: bounded retry of same-filesystem rename handles transient EPERM/EACCES/EBUSY reader/scanner sharing failures (20/40/80/160/320ms). It never deletes the destination, changes ownership, retries generation or replays approval intent. Permanent failures still fail closed. JsonMemoryStore and run/review journals use the same helper.

Ultrawide: the Flow workspace lifts its previous maximum width while forms/review text retain readable limits. Layout uses CSS pixels; Flow remains DOM/SVG vector rendering, independent of display density. Actual browser viewport and DPR checks are recorded in workspace-preflight.md, not inferred from monitor marketing resolution.
