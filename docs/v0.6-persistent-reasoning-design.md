# SCAD v0.6 — Persistent Reasoning State & Cross-Cycle Memory Design

Design and architecture investigation only. No production code, tests, or
configuration were modified. No commits were created.

- Baseline: v0.5 Reasoning & Hypothesis Evolution, commit `cb68dde`
- Scope: make SCAD's reasoning state continuous across process restarts and
  multiple reasoning cycles while preserving the v0.5 epistemic integrity
  guarantees (deterministic intelligence, explicit write scopes, immutable
  hypothesis evolution, state signatures, human governance, no hidden memory).
- Hard constraint: this is **not** a generic agent memory system. There is no
  vector store, no embeddings, no semantic memory, no autonomous learning.

---

## 1. Current architecture analysis

### 1.1 Persistence layer

`JsonMemoryStore` (`src/core/memory/json-memory.ts`) is a single-file-per-key
store: `memory/<key>.json`, pretty-printed JSON, **whole-file overwrite** on
every `save`. There is no append at the file level. `get` returns `null` on any
read/parse error (so "absent" and "corrupt" are indistinguishable today).

`ScopedMemory` (`src/core/memory/scoped-memory.ts`) enforces per-action write
scopes physically: a `save`/`remove` for a key outside the scope throws
`WriteScopeViolationError`. Scopes are exact allow-lists of top-level store
keys (keys cannot contain `/` or `\`, so one key = one file).

### 1.2 Memory keys and what they hold (v0.5)

| Key                                                       | Shape                                                                             | Written by                                              | Read by                                           | Overwrite?                             |
| --------------------------------------------------------- | --------------------------------------------------------------------------------- | ------------------------------------------------------- | ------------------------------------------------- | -------------------------------------- |
| `research`                                                | `ResearchBundle` (plan, queries, sources, evidence, claims, contradictions, gaps) | pipeline stages, `ReasoningEngine` RESEARCH actions     | pipeline resume, reasoning engine, CLI inspection | yes (whole bundle)                     |
| `intelligence`                                            | `ResearchIntelligenceReport`                                                      | `documentary.ts`, reasoning RESEARCH/hypothesis actions | reasoning engine, CLI                             | yes; kept byte-identical across cycles |
| `hypotheses`                                              | `{ hypotheses, verifications }` — **projection** of the version log               | pipeline hypotheses stage, reasoning engine             | downstream stages, trace, CLI                     | yes                                    |
| `hypothesis-versions`                                     | `HypothesisVersion[]` — immutable belief log                                      | reasoning engine (append-only semantics)                | reasoning engine, CLI                             | file overwritten, entries immutable    |
| `reasoning`                                               | `{ version: 1, state: ReasoningState }` — control cursor + full step log          | reasoning engine (`controlWrite` after every step)      | reasoning engine resume, CLI                      | **yes — latest state only**            |
| `approved`                                                | `Record<stage, { approvedAt, modified? }>`                                        | `HumanApprover` only                                    | tests, HumanApprover merge                        | record-merge                           |
| `claims`, `factCheck`, `narrative`, `visual`, `selfCheck` | pipeline stage artifacts                                                          | pipeline                                                | downstream stages, resume                         | yes                                    |

`output/` keeps exported copies (`research.json`, `reasoning.json`,
`hypothesis-versions.json`, …), derived from the memory keys by the CLI.

### 1.3 Read/write paths traced

- **Pipeline** (`src/core/pipeline.ts`): per stage, `existing = memory.get(stage)`;
  if present and not forced, **skip** (resume checkpoint); else `runStage` →
  `memory.save(stage, result)`. `--force` regenerates and overwrites.
- **Reasoning engine** (`src/agents/reasoning/reasoning-engine.ts`):
  - `run()` reads `reasoning` (resume check), `research`, `hypothesis-versions`,
    `intelligence`; pins `referenceDate`; seeds the first cycle; then loops:
    read intelligence → compute signature-before → `assessSituation` (pure) →
    `planReasoning` (pure) → approval gate → `executeStep` (scoped epistemic
    writes) → signature-after → `record` step → `controlWrite(reasoning)`.
  - Control writes (`reasoning`) go through the raw store every step; epistemic
    writes go through `ScopedMemory` with `ACTION_WRITE_SCOPE[kind]`.
  - `seedFirstCycle` writes `hypothesis-versions`, `hypotheses`, and
    `intelligence` (only if absent — else kept byte-identical).
- **Intelligence**: deterministic `ResearchIntelligenceEngine`
  (`src/agents/research/research-intelligence.ts`), pure functions only
  (evidence quality, source independence, claim confidence, contradictions,
  completeness/stopping, uncertainties, verifications). Rebuilt via
  `rebuildIntelligence` after RESEARCH/hypothesis actions; read from store
  otherwise; recomputed in-memory if absent (not persisted on read).
- **Signatures**: `computeStateSignature` = sha256 over
  `{ question, research, intelligence, hypotheses, versions, referenceDate }`,
  with volatile `accessedAt` stripped. Persisted in `cycleContext.stateSignature`
  and per-step `stateSignatureBefore/After` inside `reasoning.json`.
- **Governance**: `HumanApprover.review` on gated kinds
  (GENERATE/REVISE/REJECT/REQUEST_HUMAN_INPUT); writes `approved` directly.
  The reasoning engine never reads `approved` on resume.

### 1.4 What each artifact represents today

1. `research` — current **epistemic** gathered facts (`sources`, `evidence`,
   `claims` are collected; `contradictions`, `gaps` are deterministically
   recomputed). Overwritten on RESEARCH.
2. `intelligence` — **derived** decision-relevant analysis. Overwritten when
   its inputs change; guaranteed equal whenever inputs are equal.
3. `hypotheses` — **projection** (active pointer view) of the version log.
   Fully redundant with `hypothesis-versions` but kept for v0.4 downstream
   compatibility.
4. `hypothesis-versions` — **epistemic history**: immutable per-entry, current
   belief = `activeVersions` (latest non-rejected per hypothesis). This is the
   existing cross-cycle-ready artifact — it already survives process restarts.
5. `reasoning` — **control state** and (embedded) the **history of reasoning
   steps of the current run only**. Overwritten each step. This is the
   artifact that breaks across cycles: a new cycle would need to either replace
   it (losing old steps) or grow it indefinitely.
6. `approved` — **governance**. Merge-append per stage.

### 1.5 Gaps that motivate v0.6

- A new cycle is not representable: `buildCycleContext` hardcodes `CYC_001`;
  `run()` no-ops on any `STOPPED`/`NEEDS_HUMAN` state, and there is no rule for
  when a terminal state may legitimately be reopened.
- Reasoning history is only durable _inside_ the overwritten control file; "a
  later cycle must not rewrite the meaning of an earlier cycle" is unenforced.
- Step ids restart per run (`STEP_001` from `steps.length + 1`), so
  `HypothesisVersion.createdAfterStep` ("STEP_004") is ambiguous across cycles.
- `get` returning `null` on corruption means a torn `reasoning.json` is
  indistinguishable from "never reasoned" — recovery would silently reseed.
- `--force` deletes `reasoning`, `hypothesis-versions`, `hypotheses` —
  history-destroying semantics that cannot survive cross-cycle reasoning.
- Human reasoning decisions (reject/modify/regenerate) survive only as step
  notes; there is no durable, readable governance record that can authorize a
  future cycle.
- Reference date defaults fall back to wall clock (`new Date()`) in two places
  when nothing is pinned; acceptable today (pinned once, then inherited) but
  needs an explicit rule for v0.6.

## 2. State classification

| Category                           | Keys / artifacts                                                                  | Definition                                                                                                                                              | v0.6 policy                                                                                                                                                   |
| ---------------------------------- | --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A. Epistemic state**             | `research`, `hypothesis-versions`                                                 | What SCAD currently has grounds to believe/consider: gathered facts and the hypothesis beliefs. `hypotheses` is the projection of A for v0.4 consumers. | Loaded unchanged across cycles. Mutated **only** by an explicit scoped action executed _inside_ a cycle.                                                      |
| **B. Derived intelligence**        | `intelligence`                                                                    | Deterministic analysis of A + pinned date + budget: quality, independence, confidence, contradictions, completeness, stopping signals, verifications.   | **Always a pure function of (A, referenceDate, budget)**. Never an input to A. Recompute-or-reuse via an input signature (see §5). Never treated as evidence. |
| **C. Control state**               | `reasoning` (cursor), step ids, budgets                                           | Cycle id, reference date, budget, status, resume cursor, in-progress steps, last stopping record.                                                       | Resettable/overwritable _by the engine only_. Describes A/B, never rewrites them.                                                                             |
| **D. Historical reasoning memory** | `reasoning-history` (new), sealed steps, `hypothesis-versions`, `decisions` (new) | What happened, when, why, with which signatures and outcomes.                                                                                           | **Immutable audit log** (see §7). Consumed cross-cycle only for _eligibility_ decisions (§10), never for scores (§11).                                        |
| **E. Human governance**            | `approved`, `decisions` (new)                                                     | Human accept/reject/modify decisions, approvals, and (new) explicit answers/requests.                                                                   | Append-only. Governs whether actions run and whether a terminal state may reopen. **Never becomes automatic belief** (§11–§12).                               |

Answer to the Phase-2 questions:

- **Is intelligence epistemic or derived?** Derived. It is kept distinct from A
  today (separate key) and must stay distinct — exactly so history/memory can
  never leak into belief. Its only permitted influence is on action _selection_
  (control) and on the audit trail.
- **Is history epistemic, control, or audit?** The _actuality_ of past steps is
  an immutable audit log. The _derived consequences_ the policy needs from the
  current cycle's steps (attempted-key loop guard, research-attempted-this-cycle)
  are recomputed control views and stay per-cycle. History never feeds
  verification or confidence.
- **Is governance one thing?** It is a combination: gate status (`approved`),
  durable decision records (`decisions`), and — only when deliberately
  interpreted by an explicit lifecycle rule — a trigger for future cycles. It
  is neither epistemic (it does not assert facts) nor control (only the human
  writes it); it is its own category with its own write scope.

## 3. Cycle lifecycle

The cycle lifecycle proposed in the task is close to correct. The design adopts
it with four amendments (reconcile, eligibility gate, atomic seal, and an
explicit distinction between _paused_ and _stopped_):

```
LOAD        read project, cognitive state, science state, governance
RECONCILE   heal crash windows, migrate legacy state, ledger↔version cross-check
            (§9, §13, §14, F15)
CYCLE?      RUNNING       → continue the SAME cycle
            PAUSED        → wait for a governance resolution (§10); resume same cycle
            STOPPED       → eligibility gate for a NEW cycle (§10)
PIN         referenceDate (persisted, or explicitly supplied — never inferred twice)
SEED        new/resumed cycle → idempotently create its ledger entry header
            (cycleId, trigger, startedWith*) BEFORE any epistemic action (F3)
DERIVE      intelligence from (A, referenceDate, budget) — reuse iff input-identical
ASSESS      situation (pure, per-cycle attemptedKeys)
SELECT      action (deterministic policy; terminal verdicts are actions)
GATE        human approval for gated kinds (a/r/m/g)
EXECUTE     scoped epistemic writes; commit = effect marker (§13)
DERIVE      updated intelligence (pure) for signature-after
RECORD      append step to the in-progress cursor (control write)
TERMINAL?   SEAL CYCLE  → complete the seeded header in one atomic write
                            (steps, signatures, stopping, epistemic delta)
            → cursor compacts to {lastStopping, endedWithStateSignature,
                                  endedWithEpistemicSignature}
STOP / CONTINUE / PAUSE
```

Amendments explained:

1. **RECONCILE always runs first.** It distinguishes "absent" from "corrupt",
   reconstructs an unrecorded executed step (from the version log), and seeds
   legacy data into the ledger without touching epistemic artifacts.
2. **Eligibility gate** before a new cycle: a new cycle may start only if one of
   the five triggers in §10 holds; otherwise the terminal state is re-returned
   with no new history (answering the repeated-STOP problem).
3. **The ledger entry is seeded at cycle start and completed at seal.** An
   idempotent header write (cycleId, trigger, startedWith signatures) happens
   **before any epistemic action**, so a RUNNING cycle always has a durable
   ledger presence. **Seal completes that header in a single atomic write.**
   This resolves cursor-loss recovery (F3/F4): a RUNNING cycle is
   distinguishable from "never reasoned", and a lost cursor seals as
   `RECOVERED` via the eligibility gate — never through a silent empty-guard
   resume.
4. **Paused ≠ stopped.** `PAUSED` is a pause awaiting a governance resolution;
   the same cycle resumes when the resolution arrives (`decisions`). `STOPPED`
   is a sealed, terminal cycle.

### Definitions

- **A cycle starts** when: (a) no control state exists (first ever run), or
  (b) the prior state is terminal and the eligibility gate passes (§10), or
  (c) a new session begins because the question changed (§10, F13).
- **A cycle ends** when its final STOP step is recorded and the cycle is sealed
  into the ledger. Induction also pauses at `PAUSED`; it is sealed only
  when explicitly replaced/abandoned by an operator.
- **A new cycle differs from another invocation of the same cycle** in its
  `cycleId` (monotonic), its ledger entry, and an explicit reason field
  (`trigger: "epistemic-change" | "temporal-change" | "budget-change" |
"governance-change" | "explicit-request"`). Every other schema is the same.
- **Persisted between cycles:** A (research, hypothesis-versions) unchanged; B
  (intelligence) carried byte-identical **iff** its input signature still
  matches; governance (approved, decisions); sealed history.
- **Recomputed every cycle:** B when stale, situation, action plan, signatures.
- **Immutable across cycles:** sealed steps, sealed cycle records, hypothesis
  version entries, decision records.
- **Allowed to change:** A only via an executed scoped action; C only by the
  engine; E only by the human. Starting a new cycle **never** mutates A or B
  (required test #2).

## 4. Memory model

Four explicit slices, no generic `memory: Record<string, unknown>` anywhere
(the store keys `research`/`intelligence`/… remain typed artifacts; the slice is
a _discipline + write-scope_, not a loose bag):

```
CURRENT STATE            (overwritable by the owning write-scope only)
  epistemic   research, hypothesis-versions        (hypotheses = projection)
  derived     intelligence
  control     reasoning (cursor: cycle id, date, budget, status, in-progress steps)
  governance  approved (gate status)

HISTORICAL TRACE         (append-only, never rewritten)
  reasoning-history      cycles[] — one sealed ReasoningCycle per cycle
  hypothesis-versions    the belief log (also the source of current belief)
  decisions              governance records (answers, rejections, requests)
```

### Domain objects (minimal — every one already has a v0.5 claimant)

| Object                                    | Justification                                     | Notes                                                                                                                                                                                          |
| ----------------------------------------- | ------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ReasoningSession` (→ `reasoning` cursor) | v0.5 `ReasoningState` + cycle continuity          | adds `sessionId` (one per project+question, F13), `nextStepNumber`, `previousCycleId`, `consumedDecisionIds` (F8); scopes `steps` to the in-progress cycle                                     |
| `ReasoningCycle` (→ `reasoning-history`)  | **new** — the missing unit of cross-cycle history | sealed once; contains its steps, budget, dates, signatures, stopping, epistemic delta; `status` may be `RECOVERED` after cursor loss (F3)                                                      |
| `ReasoningStep`                           | v0.5 unchanged, plus globally unique ids          | `id = STEP_{globalSeq}`; ids never restart                                                                                                                                                     |
| `HypothesisVersion`                       | v0.5 unchanged                                    | already immutable + append-only; is the **commit marker** for hypothesis actions (§13)                                                                                                         |
| `DecisionRecord` (→ `decisions`)          | **new** — durable governance resolution           | written only by `HumanApprover`; consumed by the engine as control/eligibility input; consumed **at most once** via the cursor (F8); `message` is never an input                               |
| `EpistemicDelta`                          | **new** — derived at seal                         | version ids produced/superseded/rejected + keys written; deterministic; **cached derived projection** — recomputable from sealed steps + version log (F15), not a required persisted invariant |

No `Session`, `Snapshot`, or `Transition` objects are proposed beyond these:
state transitions are (already) the `stateSignatureBefore/After` pairs on each
step, and a dedicated `StateTransition` record would duplicate them (§8).
Changing the question is **not** a new cycle — it is a **new session** (F13):
the new session inherits `research` and `hypothesis-versions` unchanged, starts
its own cycle numbering, and opens a fresh eligibility baseline
(`trigger: "first"`).

## 5. Cross-cycle determinism

### Decision inputs (exhaustive)

```
selectAction(
  question,                 // pinned per session
  research,                 // A
  versions → active,        // A
  intelligence,             // B = pure(A, referenceDate, budget)
  steps-of-current-cycle,   // control: attemptedKeys at same signature (loop guard)
  pendingGovernance,        // decisions not yet consumed (decisionId ∉ cursor.consumedDecisionIds)
  humanInTheLoop,           // control flag
  referenceDate,            // pinned per cycle
  budget,                   // pinned per cycle
)
```

### Exclusions (explicitly NOT decision inputs)

- wall clock — except a single, recorded, volatile _provenance_ stamp (never in
  signatures, never read by the policy)
- randomness — none exists (`Math.random`/`crypto.randomUUID`/`hrtime` absent
  from `src/`)
- LLM conversation state / previous LLM output (§12)
- unrelated process memory, filesystem ordering
- **sealed history** — read only by the eligibility gate (§10), never by the
  policy or by any score (`VERIFY`, `assess`, confidence)
- `approved` gate records for _other_ pipeline stages

### Intelligence cache-or-rebuild rule

`intelligence` must be provably a pure function of persisted inputs. The
persisted artifact carries an explicit **metadata envelope** separating
deterministic content from audit metadata (F11):

```ts
interface IntelligenceEnvelope {
  version: number // schema version
  inputSignature: string // sha256(research, versions, referenceDate, budget)
  generatedAt: string // volatile provenance wall-clock, never signed
  report: ResearchIntelligenceReport // the deterministic body (byte-identical when inputs equal)
}
```

On load:

- `inputSignature` matches → reuse persisted `report` (byte-identical anyway);
- missing or mismatched → **recompute the `report` body** and persist; never
  treat the stale report as evidence (required test #10).

"Byte-identical" guarantees compare the deterministic **`report` body**, not the
envelope: `generatedAt` and a freshly computed `inputSignature` may legitimately
differ across recomputes of equal content (F11). Budget is part of the input —
changing `maxSteps` is a legitimate control-level reason for a new cycle and
correctly invalidates a report's input digest.

### Identity

```
same epistemic state (A)
+ same referenceDate
+ same budget
+ same governance (persisted decisions + humanInTheLoop)
+ same current-cycle step log
= same situation = same next action
```

The v0.5 loop guard is preserved: an action already attempted at the _same
state signature in this cycle_ is not re-attempted; if every candidate is
exhausted, the cycle terminates with `STOP_NO_ACTION`. Because `attemptedKeys`
is recomputed per cycle from that cycle's steps, a new cycle at an unchanged
signature deterministically re-terminates (see §10) — no drift, no endless logs.
Cross-run byte-identity holds given identical persisted inputs **and** identical
provider outputs (cache hit or captured fixtures); a first live ingestion is
environment-dependent, isolated by the deterministic fallbacks already present —
the guarantee scope is explicit, not implied (F17).

## 6. Time semantics

Six distinct time concepts are kept apart; only one is decision-relevant:

| Concept                                                              | Source                                                                                                                                      | Decision-relevant?                                      | Persisted?             |
| -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------- | ---------------------- |
| **`referenceDate`** (world anchor)                                   | explicit pin (`SCAD_REFERENCE_DATE` / option) → else inherited from the prior cycle's persisted date → else wall clock once, then persisted | **yes** (freshness, completeness, stopping, signatures) | yes, in `CycleContext` |
| **event dates** (historical events the research is about)            | source/evidence data                                                                                                                        | no                                                      | yes (data fields)      |
| **source publication dates**                                         | source data                                                                                                                                 | via freshness only                                      | yes                    |
| **research execution time** (`accessedAt`/`fetchedAt`/`generatedAt`) | wall clock at collection                                                                                                                    | no — stripped from signatures via `stripVolatile`       | yes, as provenance     |
| **cycle start time**                                                 | equals `referenceDate` today (`performedAt`)                                                                                                | no                                                      | yes                    |
| **persistence time**                                                 | not recorded                                                                                                                                | no                                                      | no                     |

### Anchoring rule

> Epistemic evaluation is anchored to the world as of `referenceDate`. A new
> reasoning cycle does **not** advance the temporal horizon on its own.

- Re-invoking `reason` on a terminal state with `referenceDate = D1` and
  unchanged epistemic state: deterministic re-stop at D1 (no new history).
- Setting `referenceDate = D2` is an explicit temporal-horizon change → in
  principle a _temporal-change_ trigger for a new cycle (§10); freshness scores
  then legitimately differ at D2. This is the only way the horizon advances,
  and it is always explicit.
- Wall-clock is used at most once at the very first pin and then inherited;
  once a date is persisted it is reused forever (already today's behavior via
  `resolveReferenceDate`).

## 7. Historical immutability

Append-only, at minimum, whenever a new artifact is introduced or touched:

| Artifact                                 | Rule                                                                                                     |
| ---------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| Reasoning steps (sealed)                 | immutable after seal; a step's id, signatures, action, status never change                               |
| Reasoning cycles (`reasoning-history`)   | created once by `sealCycle`, never updated                                                               |
| Hypothesis versions                      | unchanged v0.5 rule: `appendVersion` returns a new array, superseding pointer only                       |
| Human approvals / rejections / decisions | append-only records; `approved` may be re-stamped only as gate status, the `decisions` log never mutates |
| State transitions                        | `stateSignatureBefore/After` on each step and on each cycle; never edited                                |
| Stopping decisions                       | part of the sealed cycle record                                                                          |

`Cycle 003` cannot rewrite the meaning of `Cycle 001`: cycle records are sealed
on separate ledger entries, and no component holds a write scope that includes
the ledger key (`reasoning-history`) _and_ an epistemic key. Enforcement level:
(1) schema (no update method and no mutation rule exposed), (2) write-scope
(only `sealCycle` writes the ledger; the engine's action scopes never include
it), (3) invariant tests (§18, test #5).

## 8. State transitions

The existing `stateSignatureBefore` / `stateSignatureAfter` pair on every step
is kept and promoted to a first-class trace concept: it already answers "did
this action change the epistemic state, and how did it move". At step granularity:

- `signatureAfter === signatureBefore` ⇒ the action made no epistemic change
  (STOP, BLOCKED, REQUEST_HUMAN_INPUT, and — in rare cases — a RESEARCH that
  merged nothing new).
- `signatureAfter !== signatureBefore` ⇒ an epistemic mutation occurred; the
  step's `writes[]` identifies which keys, and the version log records the
  before/after belief pointers.

At cycle granularity the new `EpistemicDelta` (derived at seal, deterministic)
adds the human-readable summary: version ids produced / superseded / rejected,
keys written, and the global before/after signature. It is a **cached derived
projection** (minimality): recomputable from the sealed steps + version log, and
verified against the log by the load-time cross-check (F15) — it is not a
required persisted invariant.

No separate persisted `StateTransition` object is proposed: the (before, after,
action, writes) tuple is already a transition record and duplicating it into a
new artifact would break the "memory must not become belief" discipline (§11).

## 9. Resume vs new cycle

### RESUME (process interrupted mid-cycle)

- Same cycle id, same reference date, same budget.
- The **cursor** (`reasoning`) holds the in-progress step log; if it is intact,
  continuation is byte-deterministic (already tested for truncated runs in
  v0.5).
- If the _cursor_ is corrupt/lost but the ledger and epistemic artifacts are
  intact, a reconciliation pass rebuilds the cursor **from the version log**: it
  cannot recover intermediate audit detail it never had, but it guarantees that
  (a) no epistemic artifact is regenerated, (b) no history is fabricated, and (c)
  the run reports the recovery in the notes. See §13.
- A crash window right after an epistemic write but before its step record is
  closed deterministically for **both** action classes via the commit marker
  (§13):
  - **Hypothesis actions** (GENERATE/REVISE/REJECT): the new `HypothesisVersion`
    is the marker; its `createdAfterStep` references an unrecorded step, which
    is synthesized into a `COMPLETED` step ("recovered: effect present, step
    reconstructed after crash"). The `hypotheses` projection and `intelligence`
    are lazily rebuilt (pure) — no re-execution, no duplicate versions (F2).
  - **RESEARCH actions**: the marker is the target follow-up `query` present in
    `research.queries` (persisted in the same `research.json` save as its
    evidence). If the marker is present, the `COMPLETED` step is synthesized
    from the persisted bundle and intelligence is recomputed — **no live
    search/LLM call is re-invoked** (F1). If the marker is absent, the action
    was never committed and resumes from the start.
- If the in-progress cursor is lost for a RUNNING cycle, the cycle's **seeded
  ledger header** (written at start, §3) proves it existed; reconcile seals it
  as `RECOVERED` and the next cycle is only eligible via §10 — never an
  empty-guard silent resume (F3/F4).

### NEW REASONING CYCLE (previous cycle completed)

- New monotonic cycle id (`CYC_00N`), new ledger entry, new in-progress step
  list, fresh per-cycle attempted-keys.
- Epistemic facts (A) are loaded untouched; derived intelligence (B) is reused
  iff its input signature matches, else recomputed — never regenerated.
- Eligibility requires one of the §10 triggers. The cycle records its trigger.

Today the distinction exists only implicitly (a truncated `reasoning` state
resumes; a terminal state no-ops). v0.6 makes it explicit and durable.

## 10. Repeated STOP and cycle eligibility

### Repeated STOP

`reason` on a terminal state with unchanged inputs re-returns the terminal
state — **no new history is written**. This is today's behavior, now backed by
an explicit rule: starting a new cycle changes history, and history is
append-only, so appending is a commitment that requires a cause.

### What makes a previously terminal state eligible for another cycle

Five triggers, and only five:

1. **Epistemic change** — load-time **A-only epistemic signature** differs from
   the previous terminal cycle's `endedWithEpistemicSignature`. The A-only
   signature is `sha256({question, research[volatile-elided], versions,
activeHypotheses})`: it **excludes** `intelligence`, `referenceDate`,
   `budget`, `cycleId`, and audit timestamps, so budget/date changes,
   re-fetch metadata, and derived intelligence can never masquerade as
   epistemic change (F7). The volatile-elided subset of `research` is the
   fixed elision set from `stripVolatile` (`accessedAt`, `fetchedAt`,
   transport metadata) — everything else is signed. This covers "new evidence /
   new source" (via `scad documentary --force` research re-run or an external
   import) and any hypothesis-log change. The full state signature still drives
   the within-cycle loop guard.
2. **Temporal change** — an explicit new `referenceDate` (D1 → D2).
3. **Budget change** — explicit new reasoning `budget` parameters.
4. **Governance change** — an **unconsumed**, **non-rejected** `DecisionRecord`
    (`decisionId ∉ cursor.consumedDecisionIds`) that replaces a reasoning action
    of a **sealed** cycle (human explicitly asked for a change → a new cycle may
    attempt a _different_, deterministic alternative path — never a repeat of the
    blocked action at an unchanged signature, §18.12). Rejected decisions are
    purposely excluded from eligibility (`pendingForEligibility` filters
    `response === "rejected"`); they never auto-open a cycle — the rejection is
    recorded append-only and instead forecloses the action at the same signature
    (§20.6). **Pause resolution is not this trigger (F9):** a `DecisionRecord(answer)`
   that resolves a pending `REQUEST_HUMAN_INPUT` of a `PAUSED` cycle
   **resumes the same cycle** — no new cycle, no new ledger entry. Only a
   decision aimed at a sealed cycle's action is a new-cycle governance trigger.
5. **Explicit request** — `reason --force` (or equivalent) forces a cycle and
   is **never destructive** (F14, §14). The forced cycle has **no artificial
   one-step limit** (F6): if no epistemic candidate exists it sealingly reaches
   `STOP_NO_ACTION` as its single terminal step — a minimal, honest audit
   entry; if a valid epistemic candidate exists it runs the normal policy to
   its own stopping term.

Question change is **not** a cycle trigger (F13): the question is the session
identity (`sessionId`, §4). A different question starts a **new session**, which
inherits A/B and opens with `trigger: "first"`.

### STOP kinds across cycles

- `STOP_RESEARCH_LIMIT` — the budget was the binding constraint. Re-open via
  trigger 3 (raised budget) or 1 (new evidence).
- `STOP_CONFIDENT_ENOUGH` / `STOP_INCONCLUSIVE` / `STOP_NO_ACTION` — terminal
  until 1, 2, 3, 4, or 5 changes the decision space.
- `STOP_HUMAN_REQUIRED` / `NEEDS_HUMAN` — **paused** (`PAUSED`), not terminal.
  It resumes in-place (**same cycle**, no new history) when a
  `DecisionRecord(answer)` resolves the pending `REQUEST_HUMAN_INPUT`. A
  `PAUSED` state is _sealed_ as a cycle only when the operator explicitly
  abandons it (recorded as a decision).

No other condition opens a cycle. In particular, "some time passed" is not a
trigger.

## 11. Memory must not become belief

Enforced by construction, not by convention:

- **Verification never reads history.** `verifyPureHypotheses` and all
  `confidence`/`quality`/`independence` functions take only `research` +
  hypotheses. The intelligence report (including a previous verification) is
  an input to _action selection_, never to a re-verification of the same state.
- **Previous confidence / decisions / narratives / LLM output are not epistemic
  inputs** anywhere in the scoring path.
- **The only cross-cycle influence is control-level and gated**: the eligibility
  gate (§10) checks _whether_ to run; the loop guard uses only the current
  cycle's steps at the current signature; governance decisions change
  _candidates_, neither confidence nor verdicts.
- If historical reasoning is ever allowed to influence a future decision, the
  mechanism is: (a) it must be an explicit control input (trigger/eligibility or
  a governance decision), and (b) it must never be a score input.

Required tests #3 and #15 assert this: seeding a rich history must not raise
any hypothesis confidence, and replaying state must not drift belief.

## 12. LLM memory boundary

Default assumption, stated: **LLM conversation context is not durable epistemic
state.**

- A previous run's LLM conversation persists only as _artifacts_: sources,
  evidence, claims in `research` (written by a RESEARCH action); hypothesis
  versions (written by a gated hypothesis action); or the content cache
  (`data/cache/*`) which is a **provider cache**, replay-feed only.
- LLM-derived text that sits in an intelligence report or a step note is
  **interpretation/audit**, not evidence. It can describe belief; it cannot
  assert it.
- For any persisted LLM output the lifecycle before it may affect epistemic
  state is explicit: RESEARCH writes it as gathered fact; a gated hypothesis
  action writes it as a belief version. Every other path (reasoning drafts,
  alternative proposals, verifications, relationship overrides) is ephemeral or
  derived — Zod-validated and cross-checked, never belief.

## 13. Failure and recovery

Where atomicity/idempotency is genuinely required — and it is _not_ everywhere.
A single-file JSON store avoids a database-layer temptation; the design leans
on the isolated fallbacks already present (Scenario F: byte-identical replay).

### Authoritative commit point

> **The commit point of an epistemic action is the durable write of its effect
> marker inside the epistemic artifact itself.**

| Action                              | Effect marker (commit)                                                                                                 |
| ----------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `RESEARCH`                          | the follow-up `query` entry present in `research.queries` — persisted in the same `research.json` save as its evidence |
| `GENERATE/REVISE/REJECT_HYPOTHESIS` | the new `HypothesisVersion` entry in `hypothesis-versions.json`                                                        |

Everything else (`hypotheses` projection, `intelligence`, step records, ledger
entries) is **derived or audit** and is lazily rebuildable without re-applying
the action. Consequences:

- Marker present ⇒ the action was **committed** — recovery must never
  re-execute it (no duplicated beliefs, no re-invoked live search/LLM; F1/F2).
- Marker absent ⇒ it was **never committed** — re-running is safe.
- Steps are recorded **after** effects (write-ahead order below): a step
  without an effect is impossible by ordering; an effect without a step is
  healed by synthesis (§9).

Recovery decisions are derived entirely from persisted state (cursor, ledger,
version log, research bundle) — a recovered step is `COMPLETED` with a
`"recovered: effect present, step reconstructed after crash"` note.

### Store-level atomicity (F16)

Every `JsonMemoryStore.save` becomes **atomic replace**: write to a
same-directory temp file, then `rename` over the target. A single save is
therefore all-or-nothing, and a torn write can never masquerade as a valid
cursor/ledger entry (per-entry isolation is otherwise false for a single-JSON
ledger). `get` still returns `null` on a read/parse error, but after atomic
replaces that means "absent **or externally corrupted**" — corrupt ≠ absent is
never silently reseeded; it is surfaced for operator recovery.

### Crash windows

Ordering rule for every executed step: (1) execute in memory; (2) persist the
epistemic effect (this IS the commit — deterministic fallbacks if the LLM
failed); (3) record the step + `controlWrite`; (4) at the end, seal the seeded
ledger cycle.

| Scenario                                             | Commit point                | Recovery                                                                                                                                                                                      |
| ---------------------------------------------------- | --------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Crash before any write                               | —                           | clean resume; nothing persisted                                                                                                                                                               |
| Crash mid-RESEARCH (before save)                     | none — not committed        | marker absent ⇒ action never committed; resume re-selects the same target deterministically and runs it (its first committed attempt) — safe, no duplicate bundle                             |
| Research effect persisted, step not recorded         | target `query` in `queries` | marker present ⇒ synthesize `COMPLETED` step from the persisted bundle + recompute intelligence; **no live search/LLM re-invocation** (F1)                                                    |
| Crash between version/hypotheses/intelligence writes | new `HypothesisVersion`     | rebuild `hypotheses` projection + recompute intelligence (both pure); synthesize step; no re-execution (F2)                                                                                   |
| Epistemic mutation persisted, step not recorded      | the effect marker           | same as the two rows above (F1/F2)                                                                                                                                                            |
| Step recorded, cycle not yet sealed                  | —                           | RECONCILE completes the seeded ledger header from the cursor (idempotent seal)                                                                                                                |
| Cycle sealed                                         | ledger write                | nothing to heal; load-time cross-check (F15) confirms                                                                                                                                         |
| Cursor lost for a RUNNING cycle                      | —                           | the seeded ledger header (F3) proves the cycle existed ⇒ seal it as `status: "RECOVERED"` from versions + sealed steps; next cycle only through §10 — **never** an empty-guard resume (F3/F4) |
| Crash during human approval                          | decision write              | nothing durable until the human answers; a decision whose write did not land is not durable ⇒ re-ask (at-most-once)                                                                           |
| Crash during resume                                  | per-case (rows above)       | resume is read + derive; re-running is safe; the only frequently rewritten file is the rebuildable cursor                                                                                     |
| Corrupted ledger (external, not torn)                | —                           | atomic replace makes torn entries impossible; external corruption is surfaced loudly, isolated to that cycle entry, never reseeded (test-invariant, §17)                                      |
| Missing derived intelligence                         | —                           | recompute from (A, referenceDate, budget) — never treat as new evidence (test #10)                                                                                                            |
| Project without history / created under v0.4         | —                           | see §14                                                                                                                                                                                       |

### Load-time cross-check

RECONCILE verifies ledger ↔ belief consistency (F15): for each sealed cycle,
every `delta.producedVersionIds` exists in the version log, and every
step/`createdAfterStep` resolves to a sealed or cursor step. A mismatch is
surfaced loudly and refuses to proceed — history is audit-only, but it must not
quietly disagree with belief.

**Single atomic write** per ledger entry is the design's unit of durability;
the cursor is the only frequently rewritten file and is defined as
_rebuildable_. Atomic replaces (F16) make every single save all-or-nothing.

## 14. Migration / backward compatibility

Existing v0.4/v0.5 projects must load and run without reconstruction by the
user. Rules:

1. **No artifact is rewritten on load.** Migration is a _view_ over existing
   files until a write is actually due.
2. **Legacy `reasoning` (v1, terminal, steps embedded):** treated as an
   implicit cycle. On the next eligible new cycle, its state is archived once
   as a read-only legacy entry. To keep IDs collision-proof (F10), the legacy
   cycle keeps **its real persisted `cycleId`** (`CYC_001` for the current
   hardcoded baseline), tagged `source: "legacy-v1"`; `nextCycleId` and
   `nextStepNumber` are always derived as `max(existing ids across cursor,
ledger, and version log) + 1`, so new cycles start at `CYC_002` and new
   steps above the legacy max — namespace collision is impossible by
   construction. `STEP_000` (baseline import) is a sentinel and is never
   minted as a real step. Legacy semantics are preserved; no epistemic data is
   regenerated.
3. **Legacy `intelligence` without the envelope:** accepted once and wrapped
   into `{ version, inputSignature, generatedAt, report }` with the legacy body
   placed in `report` **unchanged** — only the documented metadata fields are
   added (F11). "Byte-identical" elsewhere in this document compares the
   `report` body, not the envelope.
4. **Legacy `hypothesis-versions`** (v0.5 shape): unchanged — it is already the
   cross-cycle belief log. `imported from the hypotheses stage` v1 entries
   keep `STEP_000`.
5. **`--force` semantics:** `--force` is redefined as **force a new reasoning
   cycle** and is **never destructive in any version** (F14). The destructive
   `remove(reasoning|hypothesis-versions|hypotheses)` path
   (`cli.ts:519-521`) is retired entirely, version-gated behind the new schema
   version; there is no destructive escape hatch. For v0.4 projects this is
   harmless — those keys simply do not exist yet. This is a deliberate,
   documented behavior change for v0.6.
6. **Missing `decisions` / `reasoning-history`:** read as empty; written only
   when an actual decision/seal occurs.
7. **Schema versioning:** every new artifact carries `version`; the load path
   validates known versions and rejects unknown ones loudly (no silent
   reinterpretation).

ReasoningCycle (key: "reasoning-history", version 1, append-only)
  cycleId: string                 // monotonic; derived from max(existing)+1 (F10)

  startedWithStateSignature: string
  endedWithStateSignature: string
  endedWithEpistemicSignature: string   // A-only signature, the eligibility baseline (F7)
  steps: ReasoningStep[]          // sealed, immutable
  stopping: StoppingRecord | null
  delta: EpistemicDelta           // derived projection, recomputable + verifiable (F15)
  source: "engine" | "legacy-v1"

EpistemicDelta (cached derived projection at seal, deterministic — not a required invariant)
  producedVersionIds: string[]
  supersededVersionIds: string[]
  rejectedVersionIds: string[]
  keysWritten: string[]

  decisionId: string              // DEC_001
  cycleId: string

  message: string                 // human-readable; NEVER a policy input (F8)

`hypotheses` stays a projection of `hypothesis-versions`; no new hypothesis

## 16. Proposed minimal API

Only the seams the existing code already implies. The `ReasoningEngine` keeps
its public `run()`. New seams:

```ts
// Load + reconciliation (new load path, replaces readReasoning)
loadReasoningCursor(store): { cursor, cycles, recoveryNotes }
   // distinguishes absent vs corrupt; heals crash windows; migrates legacy (§13/§14)

// Lifecycle
startNewCycle(cursor, { trigger, referenceDate, budget }): CycleStart | Refused
seedCycleHeader(cursor, cycle): void              // idempotent ledger header (F3)
sealCycle(cursor, cycle, stopping, delta): void   // completes the seeded header; atomic replace; idempotent
resumeCycle(cursor): CycleOutcome                   // continue or wait

// Eligibility (pure) — A-only signature, never B/date/budget/ids (F7)
isEligibleForNewCycle(prevTerminal: ReasoningCycle,
                      now: { epistemicSignature, referenceDate, budget,
                             pendingDecisions }): Inference

// Intelligence identity
resolveIntelligence(store, { research, versions, referenceDate, budget }): Report
   // reuse iff envelope.inputSignature === hash(...), else recompute+persist (F11)

// Governance consumption (control-only; F8)
consumePendingDecisions(decisions, cursor): { resolvedPause, requestedPath }
   // consumption appends decisionId to cursor.consumedDecisionIds in the SAME
   // controlWrite as the step that applies it — a decision is applied at most once
```

The changes to the existing engine are: `buildCycleContext` derives IDs from
the ledger (`CYC_00N`), steps use the session counter, `controlWrite` is split
into cursor-write and `sealCycle`, and the new-cycle eligibility gate sits where
`run()` today no-ops on terminal states. No new storage abstraction is
introduced.

## 17. Invariants

Core (must hold in every state of every run):

1. `Epistemic state ≠ control state` — distinct keys, distinct write scopes.
2. `History ≠ evidence` — verification/confidence read only (A); history reads
   only the gate.
3. `Memory ≠ belief` — no score input ever reads `reasoning-history`,
   `decisions`, `approved`, or prior `intelligence` as a _fact_.
4. `LLM context ≠ epistemic state` — LLM output becomes epistemic only through
   an executed scoped action.
5. `Intelligence = deterministic derivative` of (A, referenceDate, budget);
   `inputSignature` proves it; stale ≠ newly-stamped.
6. `Hypothesis versions = immutable history` — append-only, no in-place edit.
7. `STOP ≠ epistemic mutation` — STOP/REQUEST_HUMAN_INPUT write only
   `reasoning`; `stateSignatureAfter === stateSignatureBefore`.
8. `Human governance ≠ automatic belief update` — a decision triggers a
   cycle/candidate change; it never rewrites a hypothesis or a score.
9. Sealed cycles and sealed steps are immutable; every store save is an
   **atomic replace** (temp + rename); the ledger entry is seeded at cycle start
   and completed by a single atomic write at seal.
10. New-cycle start writes only control keys (+ the idempotent ledger seed);
    step ids and cycle ids are globally unique and derived from
    `max(existing) + 1`; eligibility compares the **A-only** epistemic
    signature, never B/date/budget/ids/audit timestamps.
11. `referenceDate` is pinned per cycle; never derived from a second wall-clock
    read.
12. Same decision inputs (§5) ⇒ same decision; `UNKNOWN`/`INCONCLUSIVE` are
    valid results; there is no forced winner, no hidden accumulation, no false
    independence, no silent contradiction resolution, no hidden temporal
    dependency, no hidden agent memory.
13. **Commit-point rule** — an epistemic action is committed exactly when its
    effect marker is durably written (`query` in `research.queries`; new
    `HypothesisVersion`). A committed action is never re-executed; recovery
    never re-invokes live search/LLM for a committed effect (F1/F2).
14. **Governance consumption** — a decision is applied **at most once**;
    consumption is recorded in `cursor.consumedDecisionIds` in the same
    `controlWrite` as the consuming step (F8).
15. **Pause ≠ new cycle** — a governance answer to a `PAUSED` cycle resumes the
    same cycle; a new cycle exists only after a sealed cycle (F9).
16. **Question = session identity** — changing the question starts a new session
    (inheriting A/B), never a new cycle in the old session (F13).
17. **Ledger ↔ belief consistency** — at load, every sealed cycle's
    `delta.producedVersionIds` and `createdAfterStep` references resolve in the
    version log; a mismatch refuses to proceed (F15).

## 20. Open architectural questions

1. **Cursor compaction at seal.** After sealing, `reasoning.steps` is cleared
   and full steps live only in the ledger. `scad reason` currently exports
   `output/reasoning.json` as the full reasoning artifact — should it now
   point at the ledger (history) instead? This changes a CLI output shape.
2. **Pause resolution UX.** A `PAUSED` state is resumed by a
   `DecisionRecord(answer)` that resolves the pending `REQUEST_HUMAN_INPUT`.
   Where does the answer come from — `--interactive`, a prompt file, or the
   existing approver keys? Does an unanswered pause expire, and how is
   abandonment recorded?
3. **`--force` semantics change — resolved (F14).** `--force` is force a new
   cycle, never destructive in any version; the destructive path
   (`cli.ts:519-521`) is retired with no escape hatch. Remaining UX question:
   exact flag naming (`--force` vs `--force-new-cycle`) and interplay with
   `-i` when a `PAUSED` cycle is pending.
4. **Intelligence `inputSignature` depth.** Intelligence is derived, so its
   input signature is implicitly covered by (A, date, budget). Should the
   state signature include the envelope's `inputSignature` value for
   defence-in-depth, or is that redundant noise?
5. **Reconstructed vs orphan steps — resolved (F1/F2/F3).** Synthesized steps
   are `COMPLETED` with a "recovered:" note; a cycle sealed after cursor loss
   carries `status: "RECOVERED"`. Remaining question: whether a per-step
   distinct status field is worth the schema churn vs the note alone.
6. **Governance-to-candidate plumbing — resolved.** Better-than-§18.12:
   rejection foreclosure uses neither a governance queue nor a new persisted
   set — the ledger's sealed **BLOCKED steps** are replayed into the current
   cycle's loop guard by `situation-assessment` as long as the state signature
   is unchanged. A forced/reopened cycle at the same signature therefore never
   re-proposes the blocked action (it deterministically terminates instead); a
   genuine signature change (new evidence, new date) genuinely re-opens it.
   This keeps the pure-policy + blocked-repeat-key-forbidden answer: no new
   state, no control drift, decisions stay unconsumed append-only evidence.
7. **Session vs project+question identity — resolved (F13).** One session per
   project+question; changing the question is a **new session** inheriting A/B
   with a fresh `"first"` baseline. Remaining question: whether several
   concurrent sessions for the same question (different dates/budgets) are ever
   needed — if yes, `sessionId` becomes an addressable key.
8. **Provenance timestamps.** The design records a single volatile wall-clock
   provenance stamp. Is that worth having at all (it must never be signed), or
   should v0.6 stay entirely wall-clock-free and rely on the pinned
   referenceDate?
9. **Ledger growth.** The ledger stores full sealed steps for every cycle,
   unchanged in size only over the rows of an array in one file. At what cycle
   count should the ledger be rolled into per-cycle files (a future
   architecture step), and is that in scope or a noted follow-up?

# Final report (summary)

- **Architecture findings.** v0.5 is already deterministic-by-construction with
  physically scoped writes and an immutable hypothesis log; the missing layer is
  a durable, sealed cycle history and an explicit cycle-lifecycle/eligibility
  model. Nondeterminism today is confined to wall-clock timestamps, of which
  only freshness (when `referenceDate` is unpinned) reaches decisions.
- **State model.** A (epistemic: `research`, `hypothesis-versions`), B (derived:
  `intelligence`, proven by the envelope `inputSignature`), C (control:
  `reasoning` cursor), D (history: sealed `reasoning-history` + belief +
  decisions), E (governance: `approved`, `decisions`).
- **Cycle model.** LOAD → RECONCILE → gate (resume / pause /
  new-cycle-eligibility) → PIN date → SEED ledger header → DERIVE → ASSESS →
  SELECT → GATE → EXECUTE → DERIVE → RECORD → complete the SEAL in one atomic
  write. New cycles exist only via five explicit triggers; repeated STOP appends
  nothing.
- **Memory model.** Four slices, five domain objects (cursor, cycle, step,
  version, decision) + derived delta — no generic memory bag.
- **Key invariants.** State ≠ control; history ≠ evidence; memory ≠ belief;
  LLM context ≠ state; intelligence purely derived (envelope); versions
  immutable (commit marker); STOP non-mutating; governance gated and consumed
  at most once; commit-point recovery without re-execution; atomic-replace
  saves; seeded ledger + RECOVERED seal; A-only eligibility; question = session
  identity; ledger↔belief cross-check; global id uniqueness; pinned dates.
