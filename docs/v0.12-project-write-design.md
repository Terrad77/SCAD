# v0.12 — shared project write ownership

Baseline: main at 553182d. This is the first implemented v0.12 increment, not the complete governed command/review UI described in v0.11-local-workspace-design.md.

A stable root-level .scad-writes directory holds per-project ownership directories. The key is a hash of normalized case-folded project ID so Windows case aliases compete for one owner. Atomic directory creation is the acquisition primitive on a local filesystem. The owner record includes a unique nonce, project, action and PID for diagnostics. PID is not proof that ownership can be reclaimed.

All public CLI commands that can generate, initialize, mutate, verify or export project files hold this ownership for the entire awaited operation, including interactive checkpoints and publication. Pure project readers remain independent. HTTP Trash and Restore use the same coordinator; their old process-local busy guard is secondary. Locks remain outside moved project directories. Snapshot and publication checks for Trash occur under ownership. Unsafe names, link directories and directories outside the resolved root are rejected. Different projects may have different owners.

Normal completion and domain exceptions release only the matching ownership nonce. Crash, missing/corrupt metadata and changed ownership fail closed. There is no automatic timeout, PID-based stealing, HTTP force-unlock or concurrent recovery promise. An interrupted operation requires operator investigation: stop all SCAD writers, inspect .scad-writes/<hash>/owner.json and the project domain journal, verify it belongs to the intended project, remove only that confirmed ownership directory, then resume through the existing CLI journal-aware command. Do not reset locks while any writer might still be running. The recovery UI is a future increment.

Supported scope: one local machine and local filesystem, upgraded CLI/server entrypoints. Network shares, old binaries, manual external edits and direct engine calls that bypass application entrypoints are not covered. Restart the server and all CLI processes after upgrading. This coordinator does not replace scoped memory, dependency signatures, approvals or publication recovery.

UI now identifies the workspace as v0.12. Package semver is unchanged because numbered architectural increments have historically differed from package version. The next implemented increment adds project creation from the workspace. Run/review UI remains future scope. No generation endpoint or invented approval capability is added here.

## Workspace project creation — 2026-10-06

POST /api/projects accepts a UUID requestId, title (trimmed, 1–200 characters) and research question (trimmed, 1–4000). Unknown fields are rejected. Authentication and exact local Origin are required before reading a JSON body, limited to 32 KiB. The project ID is project-<requestId>; titles are content rather than paths.

The shared coordinator protects this ID. A durable .scad-creates/<requestId>/request.json records the normalized request. CLI-compatible memory/output folders and project.json are staged beneath the receipt, then renamed together into the project root. The reader excludes the receipt directory. A repeated identical request returns the same project without rewriting metadata; different content is rejected. The metadata carries creationRequestId as completion evidence. A replay after Trash does not recreate the project. Restoration makes the original project available again.

An incomplete receipt or uncertain publication fails closed with an explicit recovery error. Operators must stop writers and inspect the receipt, staged files, target and ownership before recovery; there is no automatic deletion or replay of interrupted staging. Receipts are retained even after Trash. Supported filesystem and external-writer limits are those of the coordinator.

The English inline form supports field validation, busy state, persistent request errors, safe retry with the same submitted values, cancellation with focus return, and opening the created project. It reuses the existing typography, surfaces, semantic colors and 44px controls. Inputs stack on narrow screens. After an ambiguous failure, submitted values are read-only for a safe retry; check Projects and Trash before starting another request. Drafts are local component state and do not survive page reload. Creation does not run providers, generation or approvals.

## Project details — 2026-10-07

POST /api/projects/:id/settings accepts a strict requestId, expectedVersion, title and question payload with the existing loopback capability/Origin/body protections. The command holds shared project ownership, checks the current snapshot and refuses active publication or an unreadable revision journal. Title changes preserve the project ID and all other metadata. Question changes are permitted only when memory/output contain no entries; this includes unknown files. The reader provides a conservative presentation hint and the command checks the directories again under ownership.

Durable .scad-settings/<project-hash>/<requestId> receipts record normalized input and completion. Metadata is staged on the same filesystem and renamed into place. The metadata request marker reconciles a crash after replacement; a completed receipt allows a later replay without undoing subsequent edits. Conflicting content or a stale snapshot is rejected. Receipts are excluded from project listing and retained outside project/Trash directories. No automatic regeneration, approvals or recovery cleanup is introduced. The local filesystem and cooperating-writer limits above still apply.

Overview exposes an English inline Edit project details form. Validation focuses the affected field; Cancel returns focus to the trigger. Submitted values remain fixed for safe retry after an ambiguous failure. Explicit reload discards the draft. Drafts do not survive page reload. Existing material files are not rewritten.
