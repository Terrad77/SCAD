# v0.13.3 - Explicit Research continuation

The Overview Research review now offers Resume pipeline after a recorded Approve. This is an explicit, potentially paid generation action. Reject does not authorize continuation. The existing visual system, bounded reading width, native button states, English copy and CSS-pixel layouts are retained. No new motion, dependency or raster assets are introduced.

POST /api/projects/:id/resume requires the viewer session capability, exact local Origin and strict JSON {requestId, runId, expectedVersion}. The request creates a new run ID linked through resumeOf to the approved parent. The parent decision/journal is preserved. Shared project ownership serializes admission and all execution against CLI, metadata, review and other writers.

Admission requires the latest run to be a paused Research checkpoint with a completed, internally consistent browser APPROVE receipt and matching completion digest. The human ledger record must exactly match that receipt. Candidate, dependency and title/question signatures must match the checkpoint; the current Research question must match project metadata. Snapshot drift, invalid files, pending revisions and unsafe entries refuse admission. Legacy unsigned checkpoints, CLI-only approvals, rejected candidates and interrupted RUNNING jobs require operator recovery. No force or regeneration is accepted.

Execution reuses the existing documentary Pipeline. Research is skipped only through its existing content/dependency-bound human approval. The approval gate stops at the next unapproved stage, including when a candidate already exists; no automated approval is granted. A fresh project normally stops at Claims. Already approved downstream artifacts follow existing Pipeline reuse rules. This increment does not introduce browser review for those stages.

The child run journal is the durable request receipt. Exact replay returns its saved state across instances without starting execution or claiming ownership. Reusing a request ID with another parent, version or operation fails. A different request cannot bypass a newer run. An interrupted admission/execution remains unverified and requires inspection; replay never automatically restarts it. This retains the existing local-filesystem crash contract; power-loss durability is not certified.

The UI preserves immutable resume request values for a lost-response retry, disables repeated activation during admission, reports persistent errors and moves focus to run status when the continuation replaces the review. Reload discards the pending identity explicitly; the user is instructed to check run status first. The run log records the parent link. No autostart occurs on page load, Approve or refresh.

Verification evidence and remaining browser limitations are recorded in workspace-preflight.md. Work items are tracked in TODO-v0.13.3.md. Supabase, live provider configuration, cancellation, regeneration and other-stage browser approvals remain outside scope.
